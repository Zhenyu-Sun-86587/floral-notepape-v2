# 笺影 Mac 1.8.8：小组件性能与待办交互

本阶段把已在真实 WidgetKit 中通过人工验收的私有容器路线接入正式 Folio 构建，沿用 `dev.hermes.surface` 和原笔记目录。Windows 不启用 WidgetKit、容器监听或待办写回；Mac 使用独立模块与编译条件。

## 性能对比

基线为 `16f1e88`（1.8.7）。在本机使用相同虚构正文、32 张快照便签、相同分页尺寸，编译优化后的原生 Swift 程序，每种运行三次取中位数：

| 测量项                   |           优化前 |           优化后 |
| ------------------------ | ---------------: | ---------------: |
| 不变快照读取/解码        |   0.670–0.680 ms |   0.032–0.035 ms |
| 相同正文与尺寸的重复分页 | 26.213–26.875 ms |   0.020–0.025 ms |
| 首次分页（冷缓存）       | 52.788–53.649 ms | 48.135–54.265 ms |

两轮测量的渲染文字、分页和行高逐项相同。前两项约减少 95% 和 99.9% 的该部分耗时；首次分页的差异可能属于运行波动，不宣称冷启动性能提升。这是原生数据/分页热路径微基准，不是系统 WidgetKit 的完整交互延迟、GPU 占用或整机耗电降幅。

原正式版与实验版扩展检查时瞬时 CPU 均为 0%，驻留内存约 49 MiB 与 59 MiB。它们的展示内容、运行时间与系统缓存不同，因此这些数字不能证明两种数据容器方式的内存成本差异。

复现：`python3 scripts/benchmark-macos-widgets.py --baseline 16f1e88`。基准只使用临时虚构数据，不读实际笔记。

## 优化范围

- 快照只缓存一份，最多 1 MiB。每次调用检查文件修改时间、大小和 inode，原子替换、删除、损坏或授权撤销不会长期沿用旧快照。没有定时读取。
- Markdown 分页采用最多四份布局的 LRU 缓存，键包括正文、尺寸和字号；翻页复用现有布局，正文变化时重新计算。
- 读取快照不再重复创建目录；实验读取日志只在重新解码时产生。
- 原有 500 ms 事件合并增加两秒最长等待，持续编辑仍会发布新内容。未变化的快照仍不写文件、不请求刷新。
- 小组件时间线保持 `.never`，待办操作使用原生文件系统事件唤醒主程序，没有后台轮询或持续动画。

## 待办交互

原生小组件中 `- [ ]`、`* [ ]`、`+ [ ]` 待办行点击完成，再次点击取消；普通段落保持点击复制。Markdown 复制、当前页复制、翻页与显式展开按钮保留。代码块和引用中的示例不作为待办操作。

小组件仅在自己的容器写入有容量上限的操作队列；主程序处理后删除操作，使用原有笔记保存服务写回。关闭主界面仍可处理；主程序完全退出时，尝试通过 NSWorkspace 静默启动同一主程序。主程序核对共享授权、UUID、原文及行位置，失效的操作拒绝写回并刷新；外部 Markdown 继续使用 revision 冲突检查。Mac 内部笔记保存串行，避免自动保存与待办写回交错。

未保存的窗口草稿保持本地，不强制覆盖。打开的干净 Mac 便签窗口接收更新通知；外部文件继续使用现有文件监听同步。小组件不会直接修改原笔记文件。
